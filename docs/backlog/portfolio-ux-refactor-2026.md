- ~~Verify all interactive elements meet 40px/44px min tap target (design-system.md accessibility notes)~~ — Done 2026-08-03. Audit found two violations: `SegmentedLinks` segments at `h-8` (32px) and the `GlobalNav` language/theme controls at `h-9` (36px), both under the documented 40px floor. Both raised to `h-10` (40px) rather than carving out a density exception in the doc — the compact CV role selector was the only argument for 32px, and 8px of extra track height is a cheaper price than a documented exception that the next dense control would inherit by default. Buttons and ButtonLinks were already `h-11` (44px). Guarded in CI by `scripts/check-tap-targets.sh` (new `Check tap targets` step) — the 58 existing tests are all cv-engine and would pass identically at `h-2`, so nothing was stopping this from silently regressing.
  - **Reopened and finished 2026-08-09.** The claim above that "every interactive element in the app is now ≥40px" was wrong, and the grep could not have told us: it only fired on a line carrying both a `focus-visible:` class and a too-small `h-*`, so it was blind to a control with **no height class at all** — which is what every remaining violation was. Measuring the rendered pages at 375px found 20 more, including all six `GlobalNav` primary links at 20px, on every route.
  - Fixed two ways. Chrome that can afford the height — `GlobalNav` primary links, the CV toolbar back link, `ProjectCard` link rows, the CV header contact block, the error/404 secondary links — became real `h-10` controls. Links in prose or on a shared baseline — the homepage "See all projects", the contact page `<dd>` links — got a `.tap-reach` utility (`globals.css`) that extends the hit area with an `::after` band and leaves the text where it is.
  - The grep is deleted. `apps/portfolio-web/e2e/tap-targets.e2e.ts` replaces it: it renders every route at 375px and 1280px, and asserts each focusable element is ≥40px tall (box or `.tap-reach` band) and actually reachable 15px either side of its centre. The lesson worth keeping is that the old check asserted an implementation detail — "no line pairs these two class strings" — while everyone read it as the property "every control is ≥40px". A green light on the former says almost nothing about the latter.
- ~~Check color contrast (WCAG AA) on teal accent against both light and dark surfaces~~ — Done 2026-08-03 as part of the dark-mode audit. Accent on page is 5.24:1 light / 12.77:1 dark; every token pair the app uses was computed in both themes. Tightest margins to respect when adjusting neutrals: subtle text on page (4.63:1 light) and the segmented-control track border (3.08:1 dark).
  - **Re-verified and locked down 2026-08-09.** Unlike the tap-target claim above, this one held: recomputing every teal pair matched the recorded figures exactly, and sweeping the rendered pages found the accent resolves to only four distinct colour pairs in practice, all passing. Now enforced by `apps/portfolio-web/e2e/contrast.e2e.ts`, which walks the real DOM on eight routes in both themes rather than checking the token table, so a component pairing accent text with a surface nobody has combined before is measured too.
  - Light mode is the binding constraint for the teal specifically, tighter than the summary above suggests: focus ring on surface-muted is **3.41:1** against a 3.0 floor, and accent text on surface-muted is **4.98:1** against 4.5. Dark has 5-10x headroom everywhere. If you touch `--color-focus`, `--color-accent`, or `--color-surface-muted`, light mode is what will break.
  - Trap worth knowing before writing any test that reads colour: `color`, `background-color`, and `outline-color` are all in Tailwind's `transition-property` list, so a measurement taken in the same tick as a state change returns a blend of two tokens that exists in no palette — `rgb(162,202,199)` partway between `#ffffff` and `#0f766e`, or a focus ring reading as `currentColor`. It cost two false "confirmed WCAG failures" and a 40%-flaky suite before being pinned down. The test emulates reduced motion, which collapses the durations through the app's own `globals.css` rule.
- ~~Confirm `prefers-reduced-motion` is respected wherever transitions exist~~ — Done 2026-08-03 during the motion pass: the `globals.css` baseline already matched the guidelines doc; verified in the compiled CSS that no `@keyframes` or `infinite` animation exists anywhere. The pressed-state transform uses `motion-safe:` because the global block only zeroes durations, which would otherwise leave reduced-motion users an instant 1px jump.
  - **Re-confirmed and locked down 2026-08-09.** Held up: 0 of 1331 elements animate under `reduce` across seven routes, all three `translate-y-px` uses are `motion-safe:`-guarded, `scroll-behavior` is `auto`, and there are no JS motion APIs (`scrollIntoView`, `.animate()`, `behavior: "smooth"`) anywhere.
